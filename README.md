# Mini Factory

Mini Factory 是一个浏览器端的自动化产线教学小游戏。玩家需要拖拽设备、连接工序，并在限定时间内让合格螺栓到达成品出口。

当前版本为 **v0.3**，包含三章共十五关、本地进度与布局草稿保存、通关解锁、确定性订单场景刷新恢复，以及自动化回归测试。第三章把设备磨损、计划维护和单维修队优先级正式拉进产线——机器终于不再假装永动机。

线上试玩：<https://mini-automation-factory-bolt-v01.ond6468.chatgpt.site>

## 快速开始

需要 Node.js `>=22.13.0` 和 npm。

```powershell
cd game
npm install
npm run dev
```

开发服务器启动后，按终端显示的本地地址访问游戏。Windows PowerShell 中也可以使用 `npm.cmd run dev`。

## 常用命令

以下命令都在 `game/` 目录执行：

| 命令 | 用途 |
| --- | --- |
| `npm run dev` | 启动本地开发服务器。 |
| `npm run build` | 构建生产产物。 |
| `npm test` | 构建并运行 Node 单元测试。 |
| `npm run lint` | 运行 ESLint 静态检查。 |
| `npm run install:e2e` | 安装 Playwright Chromium（首次一次）。 |
| `npm run test:e2e` | 运行 Playwright 浏览器端到端回归测试。 |

完整验收顺序：

```powershell
npm.cmd test
npx.cmd tsc --noEmit
npm.cmd run lint
npm.cmd run build
npm.cmd run test:e2e
```

如果本机 4175 端口已被占用，改用独立端口运行 E2E：

```powershell
$env:E2E_PORT = "4176"
npm.cmd run test:e2e
```

## 已完成内容

- 十五关自动化产线玩法：第一章第 1～5 关讲基础产线，第二章第 6～10 关讲订单调度，第三章第 11～15 关讲设备可靠性；
- 第一章包含障碍、运输距离、分流/汇流、产能和质量要求；
- 第二章包含订单到达、待排区、生产队列、独立截止时间、固定种子设备库顺序与重试换局；
- 四种产品路线：普通螺栓直接交付，精密螺栓经钻孔，防锈螺栓经镀层，强化螺栓经热处理；
- 第三章加工设备在 60% 磨损时预警、85% 时加工耗时增加 20%、100% 时故障；计划维护 4 秒，故障抢修 7 秒；
- 全厂共用一支维修队，所有等待任务都可上移、下移；只有等待中的计划维护可取消，故障抢修和正在执行的任务不可取消；
- 第三章每关都会明确显示计划维护验收目标，第 12 关还要求实际调整一次维修队列；只靠故障抢修硬扛不算学会可靠性管理；
- 设备卡片不可重叠，连接时间标签保持可读；
- 已解锁关卡、最佳时间和稳定布局草稿的本地保存与刷新恢复；
- v1/v2 存档会迁移为 v3：保留旧进度、布局、最佳成绩和第二章种子，并统一写入 `orderScenarioSeeds`；
- 第 6～10、13～15 关刷新保留布局、订单场景种子和设备库顺序，但不保留运行中的订单、物料、磨损、维修队列或计时；
- 清除进度的二次确认；
- 单元测试和 Playwright E2E 回归覆盖核心流程。

四类产品的完整路线是：

- 普通螺栓：钢棒源 → 切割机 → 车削机 → 成品出口；
- 精密螺栓：钢棒源 → 切割机 → 车削机 → 钻孔机 → 成品出口；
- 防锈螺栓：钢棒源 → 切割机 → 车削机 → 镀层机 → 成品出口；
- 强化螺栓：钢棒源 → 切割机 → 车削机 → 热处理炉 → 成品出口。

详细规则、存档行为、排错和测试说明见 [`game/README.md`](game/README.md)。

## 人工验收

自动化通过后，建议再手动过一遍这些关键点：

- 第 11 关等车削机进入 60% 预警后安排计划维护，确认没有阻断弹窗，维护完成后仍能通关。
- 第 13 关排入强化螺栓订单，确认物料经过热处理炉后完成；绕过热处理不能交付。
- 第 15 关摆齐九台设备、接通四类产品路线，实际调整订单和维修队列，并确认至少一次计划维护后仍可通关。
- 额外确认旧 v2 存档升级后，第 6～10 关订单种子、已解锁进度、布局和最佳成绩没有失忆。

## 发布方式

本项目当前发布到 **ChatGPT Sites**，线上站点与 [`.openai/hosting.json`](.openai/hosting.json) 中的项目绑定关联。

发布流程是：验证当前代码 → 保存站点版本 → 部署该版本到生产地址。它不依赖 GitHub 自动发布，也不需要执行 `wrangler deploy`。项目中保留的 Cloudflare/Vinext 相关配置主要用于兼容运行环境和本地构建。

## 发布状态

v0.3 的代码与验收在本地完成后，仍需人工通过第 11、13、15 关，再单独批准合并和 ChatGPT Sites 部署。仓库验证通过不等于线上已经更新——发布按钮不是薛定谔的猫。
