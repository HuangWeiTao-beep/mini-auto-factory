# Mini Factory v0.3

Mini Factory 是一个三章十五关的自动化产线教学游戏。第一章让玩家学会摆产线、接工序、避障和分流；第二章把麻烦升级成订单调度；第三章再补上设备磨损、维护窗口和全厂唯一一支维修队。

v0.3 提供稳定、可保存进度、可复盘订单场景和可回归验证的三章体验。本版本仍不包含账号、云同步、排行榜、随机突发故障、AGV、仓储或移动端专门适配。

## 环境要求

- Node.js `>=22.13.0`
- npm

在本目录安装依赖：

```powershell
npm install
```

## 安装与本地启动

启动开发服务器：

```powershell
npm run dev
```

终端会显示本地访问地址。停止服务时按 `Ctrl+C`。

## 常用命令

| 命令 | 用途 |
| --- | --- |
| `npm run dev` | 启动本地开发服务器。 |
| `npm run build` | 构建生产产物，并生成 Cloudflare/Wrangler 部署描述。 |
| `npm run start` | 启动已构建的生产服务器。 |
| `npm test` | 构建项目并运行 Node 单元测试。 |
| `npm run lint` | 运行 ESLint 静态检查。 |
| `npm run install:e2e` | 下载 Playwright Chromium；首次运行浏览器测试时执行一次。 |
| `npm run test:e2e` | 启动临时本地服务器并运行完整 Playwright 浏览器回归。 |

Windows PowerShell 下也可以写成 `npm.cmd run test`、`npm.cmd run lint` 或 `npm.cmd run test:e2e`。

完整浏览器回归包含多条真实通关流程，第三章综合验收会运行确定性时钟和真实 UI 操作，可能需要数分钟。若 Playwright 提示找不到 Chromium，先运行：

```powershell
npm.cmd run install:e2e
```

Playwright 会默认占用 `4175` 启动临时服务；如果该端口被占用，不要拿未知旧服务凑合，直接指定空闲端口：

```powershell
$env:E2E_PORT = "4176"
npm.cmd run test:e2e
```

测试不会复用未知服务，避免把旧页面误当成当前工作树的目标。

## 玩法与关卡

1. 从左侧设备库把设备拖到画布；设备不能与障碍或其他设备重叠。
2. 点击一台设备的橙色输出端口，再点击下一台设备的蓝色输入端口完成连线。
3. 点击“开始生产”后，布局会锁定；此时不能拖动设备或修改连线。
4. 点击“暂停生产”后可以调整布局。只要改动过布局，下一次启动会从零开始生产。

三章关卡按以下节奏递进：

- 第 1 关：基础直线产线，学习放置、连接和生产。
- 第 2 关：加入钻孔机与质检要求。
- 第 3 关：两条支路分流，处理产能压力。
- 第 4 关：避开障碍，连接距离会影响运输时间。
- 第 5 关：在障碍与双支路压力下完成工坊验收。
- 第 6 关：订单看板，学习订单到达、加入队列与截止时间。
- 第 7 关：双线调度，开始处理不同截止时间和并行支路。
- 第 8 关：镀层介入，引入防锈订单和镀层机。
- 第 9 关：混单瓶颈，在钻孔与镀层共享节拍下排产。
- 第 10 关：总装排程，综合处理全部产品与交付窗口。
- 第 11 关：预防维护，识别预警并在车削机故障前维护。
- 第 12 关：维修冲突，为车削机和钻孔机调整单维修队顺序。
- 第 13 关：热处理试产，引入强化螺栓和高磨损热处理炉。
- 第 14 关：四线协同，同时调度四种产品、冗余设备与维修优先级。
- 第 15 关：可靠性审计，综合处理订单、磨损、停机窗口和备用产能。

第二、三章共有四条固定产品路线：

- 普通螺栓：钢棒源 → 切割机 → 车削机 → 成品出口
- 精密螺栓：钢棒源 → 切割机 → 车削机 → 钻孔机 → 成品出口
- 防锈螺栓：钢棒源 → 切割机 → 车削机 → 镀层机 → 成品出口
- 强化螺栓：钢棒源 → 切割机 → 车削机 → 热处理炉 → 成品出口

第 6～10 关会在运行中按时间到单。新到订单先进入“待排订单”，玩家可以把它们加入“生产队列”，并在尚未投料前上下调整顺序。钢棒源只会给队首订单投料；一旦投料，订单就进入 `inProduction`，不能再插队或撤回。运行中设备与连线依旧锁定，只有订单队列还能继续改。

第 13～15 关沿用相同的确定性订单调度，第 11～12 关则使用固定产量目标。第三章只有加工设备会磨损：完成一次加工后才增加磨损，运输、等待和空闲不磨损。状态阈值固定如下：

- 0%～59%：正常速度；
- 60%～84%：预警，速度不变；
- 85%～99%：高危，本次新开工加工耗时增加 20%；
- 100%：当前物料仍有效，随后设备故障并拒绝接料。

计划维护耗时 4 秒；没有提前安排而触发的故障抢修耗时 7 秒。全厂共用一支维修队，同一时间只处理一台设备。所有等待任务都可以上移、下移；只有等待中的计划维护可以取消，故障抢修和已经开始的任务不能取消。请求维护后，机器会做完手头物料再停机，别指望维修工隔空拧螺丝。

每个第三章关卡都会在维修面板明确显示计划维护验收进度；第 12 关还要求至少实际调整一次维修队列。产量够了但维护目标没完成也不会验收——靠机器坏了再抢修，严格说不叫“可靠性管理”，叫“消防演习”。

## 本地进度与清除

游戏使用当前浏览器的 `localStorage` 保存以下本地数据：

- 已解锁关卡；
- 各关最佳完成时间；
- 当前关卡在非运行状态下的设备布局和连线草稿；
- 第 6～10、13～15 关的 `orderScenarioSeeds`，用于固定订单表和设备库顺序。

生产运行中的瞬时物料、订单状态、磨损、维修队列、维护进度和计时不会保存；刷新后会恢复最近一次稳定布局和订单场景种子，而不是半截生产现场。v1/v2 存档会自动迁移为 v3，保留旧进度、布局、最佳成绩和第二章 `chapterTwoSeeds`，并把有效种子统一写入 `orderScenarioSeeds`。点击“重新挑战”会生成新种子，订单表和设备库顺序一起换局。数据只保存在当前浏览器和设备中，不会云同步或跨浏览器迁移。

右上角“清除进度”会先弹出二次确认。取消不会改动任何进度；确认后会删除本地存档并回到第 1 关。

## 发布到 ChatGPT Sites

本项目当前使用 **ChatGPT Sites** 发布，线上站点由根目录 [`.openai/hosting.json`](../.openai/hosting.json) 中的项目绑定关联。发布流程是：验证当前代码、保存一个站点版本、再将该版本部署到生产地址。

这不是 GitHub 自动发布流程，也不需要运行 `wrangler deploy`。项目保留的 Vinext、Cloudflare Vite 插件和 [`worker/index.ts`](worker/index.ts) 用于兼容运行环境、本地开发和构建；当前版本未配置 Cloudflare D1 数据库或 R2 存储。

## 发布验收与常见问题

自动验收顺序：

```powershell
npm.cmd test
npx.cmd tsc --noEmit
npm.cmd run lint
npm.cmd run build
npm.cmd run test:e2e
```

自动测试通过后，仍建议人工检查：

- 第 11 关：关闭可靠性说明后刷新一次，确认说明不会自行重开；运行到车削机 60% 预警，确认没有弹窗，安排 4 秒计划维护后完成关卡。
- 第 13 关：接通普通、精密和强化路线，排入强化订单，确认 `.machine--heatTreater` 实际加工且完成区出现对应订单；全程不应出现错误路线警告。
- 第 15 关：摆齐合法九设备布局并接通四种路线，按截止时间调度订单，至少执行一次计划维护和一次维修优先级判断，确认最终成功结算。
- 用旧 v2 存档启动一次，确认第二章种子、布局、最佳成绩和解锁进度迁移后仍在；刷新不应恢复半截维护现场。
- 额外看看窄窗口下的关卡按钮、控制栏、设备卡片、订单面板和连接时间标签是否仍可阅读和操作。

如果任一自动命令失败，请保留完整输出后定位失败项。不要靠“再运行一次看看”把问题赶出门——它通常会从窗户爬回来。
